# Sales History With Filters — Implementation Plan (feat_25)

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Turn `web/orders#index` into a global sales history where an order collected today surfaces first, regardless of when it was created.

**Architecture:** A new `orders.settled_on` date column records when an order's balance reached zero, stamped from inside `Order#refresh_status_from_balance!` so no service signature changes. The index gains four filters (Tipo, Estado, Período, búsqueda por N° de nota) where **the status filter selects which date the list is sorted and filtered by** — collected orders sort by `settled_on`, everything else by `sale_date`.

**Tech Stack:** Rails 7.2, PostgreSQL, HAML, TailwindCSS, Pundit, pagy, RSpec + FactoryBot.

**Spec:** `docs/superpowers/specs/2026-07-25-sales-history-filters-design.md`

  def refresh_status_from_balance!
    return if cancelled_status?

    new_status = outstanding_balance <= 0 ? "confirmed" : "pending"
    new_settled_on = new_status == "confirmed" ? payments.maximum(:payment_date) : nil
    return if status == new_status && settled_on == new_settled_on

  scope :by_type, ->(type) { where(order_type: type) if order_types.key?(type.to_s) }
  scope :by_status_filter, ->(status) { where(status: status) if statuses.key?(status.to_s) }

```ruby
    def search_mode?
      params[:paper_number].present?
    end

    def filtered_orders
      base = Order.includes(:customer, :user, order_items: :product)
      return base.search_paper(@search).order(sale_date: :desc, id: :desc) if search_mode?

      scoped = base.by_type(@type).by_status_filter(@status)

      case @status
      when "confirmed"
        scoped.settled_between(@from, @to)
              .order(Arel.sql("settled_on DESC NULLS LAST, id DESC"))
      when "pending", "cancelled"
        scoped.sold_between(@from, @to).order(sale_date: :desc, id: :desc)
      else
        scoped.order(sale_date: :desc, id: :desc)
      end
    end

    # Todas and search mode deliberately return no range: they are the modes
    # whose purpose is not to narrow.
    def resolve_period
      return [ nil, nil, false ] if @status.blank?

      case @period
      when "today"      then [ Date.current, Date.current, false ]
      when "this_month" then [ Date.current.beginning_of_month, Date.current.end_of_month, false ]
      when "custom"     then custom_range
      else [ Date.current.beginning_of_week(:monday), Date.current.end_of_week(:monday), false ]
      end
    end

    def custom_range
      from = parse_filter_date(params[:from])
      to   = parse_filter_date(params[:to])
      return [ nil, nil, true ] if from && to && from > to

      [ from, to, false ]
    end

    rescue ArgumentError, TypeError
      nil
    end
```

## Notes for the reviewer

- The `id` tiebreaker is mandatory on all three ordering branches. Both dates are `date` columns, so ties within a day are the norm; without it, pagination repeats and skips rows.
- `settled_on` is the **maximum** `payment_date`, not the payment that closed the balance. Deliberate.
- `settled_on` is a `date`, not a `datetime`. Deliberate — the app runs in UTC and midnight timestamps have caused off-by-one bugs before.
- The backfill lives only in the migration. No rake task, no model method: a migration must not depend on application code that can change later.
- There is exactly one empty state. Defaults are always applied, so "todavía no hay ventas" is unreachable.
- `web/orders/show` mislabels `on_account` orders as "Cuenta Corriente" in its Tipo field. Pre-existing bug, deliberately out of scope.
